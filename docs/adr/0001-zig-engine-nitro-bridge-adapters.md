# 1. A Zig engine behind a C ABI, a Nitro bridge, and chains as TypeScript adapters

Accepted.

## Context

React Native apps that touch blockchains need hashing, secp256k1 and Ed25519 signatures, BIP-39 seeds and HD
derivation, and then each chain's addresses and message formats. The usual answer is JavaScript (`@noble`, `@scure`,
ethers, viem): portable and well reviewed, but every key lives in the JS heap, and the curve arithmetic runs on the JS
thread.

The goal: one native engine for every chain, keys that JavaScript never holds, an API typed per chain, and new chains
added without touching the engine.

## Options

1. **JavaScript only** (`@noble`/`@scure`). Simple, audited. Keys in the JS heap; no native isolation to speak of.
2. **A native module per platform** (Swift/Kotlin wrapping platform crypto or a C library). Two implementations to
   keep equal; neither platform's crypto offers secp256k1.
3. **C or C++ libraries called straight from a C++ Nitro module.** One codebase, but the cryptographic glue (BIP-39,
   BIP-32, SLIP-0010, handle management) would be C++ written for the occasion.
4. **Rust behind uniffi or a C ABI.** Mature crypto crates; a second toolchain, a heavier build, and nothing in these
   repositories uses it.
5. **Zig behind a C ABI, a thin C++ Nitro bridge, TypeScript adapters.** Zig cross-compiles every target from one
   machine with no external toolchain, compiles C (libsecp256k1) itself, has audited-quality primitives in its
   standard library (SHA-2, Keccak, Ed25519, PBKDF2), and is already this repository family's engine language
   (zyplot).

## Decision

Option 5.

- **The engine** owns all cryptography and all secrets, behind a versioned C ABI with opaque handles. It knows
  curves, hashes and derivation schemes, never chains.
- **The bridge** is three C++ Hybrid Objects generated by nitrogen, with no logic of its own. C++ rather than Swift
  and Kotlin: one implementation for both platforms, and the C ABI is C.
- **The facade** is TypeScript over a host interface, so the same code runs on the native module and on a WebAssembly
  build of the engine ([ADR 3](0003-webassembly-test-host.md)).
- **Chains are adapters**: TypeScript packages over `@hzblj/nitro-crypto/adapter`, each declaring the capabilities it
  needs, registered at runtime into a registry that is typed per chain at compile time.
- **No Expo module, no config plugin.** Nitro modules autolink as React Native modules; nothing in the native build
  needs configuring.

## Consequences

- A chain whose primitives exist is a new package and nothing else (TRON in the example app is the proof).
- A chain needing a new primitive is an additive engine change: a function, a capability bit, no ABI break.
- The engine ships prebuilt for every target, so apps need no Zig; contributors need Zig 0.16.0 exactly, and the
  build works around three Zig 0.16 rough edges (archive alignment for Apple's linker, file modes in archives,
  libc headers for cross targets), documented in [compatibility.md](../compatibility.md).
- The engine is new code over reviewed primitives: BIP-39, BIP-32, SLIP-0010, RIPEMD-160 and the handle table are
  this repository's, which is why everything is tested against published vectors, Wycheproof and independent
  implementations, and why nothing here claims to be audited.
